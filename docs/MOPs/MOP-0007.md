## Summary

Five recipe search/recommendation RPCs are built (`search_recipes_semantic`, `search_recipes_text`, `find_similar_recipes`, `search_recipes_by_ingredients`, `get_recipe_recommendations`) but only the chat agent uses them. The Recipes page does title-only `includes()` search and has no similar-recipes affordance. The meal planner has no recipe-suggestion feature. Reactions are write-only.

This MOP closes those gaps **with the right tool per surface**, not by indiscriminately wiring RAG everywhere. See [docs/RAG_AUDIT.md](../RAG_AUDIT.md) for the per-surface evaluation and mechanism choice rationale.

**Key revision from the original draft:** the Recipes page search bar gets full-text (`search_recipes_text`), NOT semantic RAG. Semantic adds 250-500ms latency for a query type that doesn't benefit on personal collections — full-text catches title + ingredients + instructions for 30-80ms with zero LLM cost. RAG is reserved for the surfaces where it genuinely earns its keep: the chat agent (already shipped), recipe save deduplication (already shipped), the "similar to this" rail (new), and the meal planner suggestion re-ranker (new, optional Phase 2).

## Scope of Work

### Phase 1: Search bar → full-text
**Files affected:** `src/components/recipes/RecipeList.tsx`, `src/services/api.ts`

Replace the client-side `recipe.title.toLowerCase().includes(query)` filter with a server-side full-text search via the existing `search_recipes_text` RPC.

Implementation:
- Add `apiClient.searchRecipesText(query: string, limit?: number)` method calling the RPC. Use `auth.uid()` — the RPC currently accepts a `user_id` param, which must be migrated to use `auth.uid()` (see "Open issue" below).
- Add `useRecipeTextSearch(query: string)` hook that debounces input (~200ms) and calls the method.
- `RecipeList.tsx` calls the hook when `searchQuery` is non-empty; falls back to existing client-side filtering when query is empty.
- Filter chips (dietary, prep time, difficulty) continue to apply client-side on top of the search results — they're already wired and work fine post-search.

Latency target: ≤ 100ms p95 for queries on collections up to 500 recipes.

### Phase 2: Similar-recipes rail on RecipeDetail
**Files affected:** `src/components/recipes/SimilarRecipesRail.tsx` (new), `src/components/recipes/RecipeDetail.tsx`, `src/services/api.ts`

Render a horizontally-scrollable rail of up to 5 similar recipes below the recipe content, backed by `find_similar_recipes`. This is the **clearest RAG win** in the audit — one vector lookup (no query embedding needed at runtime), ~50-100ms, no good lexical equivalent.

Implementation:
- Add `apiClient.findSimilarRecipes(recipeId: string, limit?: number)` method calling the RPC. Default `match_threshold = 0.6`, `match_count = 5`.
- Add `useFindSimilarRecipes(recipeId: string)` hook.
- New `SimilarRecipesRail` component renders thumbnail cards (title + image + similarity badge).
- Hide rail entirely if zero results or if the recipe has no `embedding_vector` (recently edited; will repopulate on next backfill).
- Empty state for recipes without embeddings: don't show the rail at all (don't show "no similar recipes found" — that's confusing).

### Phase 3: Reactions feed into recommendation scoring
**Files affected:** `supabase/migrations/*recommendations_with_reactions.sql` (new, LOCAL — HARD RULE: not pushed), `src/services/api.ts`

Update `get_recipe_recommendations` to factor `recipe_reactions` into the scoring formula. Currently the RPC scores by (difficulty match) + (tag overlap) + (rating) + (prep_time fit). Add a fifth term: (reaction signal).

Proposed scoring:
```sql
-- Per recipe: average reaction signal
--   thumbs_up =  +1.0
--   thumbs_down = -0.7  (asymmetric: a single dislike doesn't bury forever)
--   no reaction = 0
-- Then bounded to [0, 1] and added to the existing 4-term score (divided by 5.0 instead of 4.0).
```

Open question for the user: should thumbs_down hard-exclude (don't surface at all) or soft-demote (current proposal)? See audit doc §Open questions.

### Phase 4: Meal planner "Suggest meals for this week"
**Files affected:** `src/components/meal-planning/SuggestWeekModal.tsx` (new), `src/pages/MealPlanner.tsx`, `src/services/api.ts`

Add a "Suggest meals" entry point on the planner that opens a modal:
- Modal asks: how many days, which slot (defaults to dinner), any constraints (max prep time, exclude tags)
- Calls `get_recipe_recommendations` with the household's stored preferences + reactions (Phase 3) + the modal constraints
- Returns top N scored recipes; user can drag/click to assign to slots, with "fill rest randomly from top 20" as a shortcut
- This is the primary scoring path — pure SQL, fast, no LLM cost
- **Phase 4b (optional, deferred):** add an embedding-based re-rank on top — given a "seed recipe" the user likes, re-rank the top 20 by embedding proximity. Defers to a Phase 2 MOP.

## Open issues to address during implementation

### `user_id` parameter on existing RPCs

`search_recipes_semantic`, `search_recipes_text`, `find_similar_recipes`, `search_recipes_by_ingredients`, and `get_recipe_recommendations` **all accept a `user_id` UUID parameter** (verified against migration 004). This is a privilege-escalation vector — a malicious caller could pass any UUID and get that user's recipes (RLS is bypassed because the RPCs are `SECURITY DEFINER`-shaped though not explicitly marked).

**Fix:** during Phase 1's migration work, update each wired RPC to use `auth.uid()` internally instead of accepting a `user_id` arg. This is the same pattern as MOP-0002's RPC consolidation and MOP-0014's atomicity work.

This is a **hard gate** — implementation cannot ship without it.

### Orphan RPC: `search_similar_recipes` (384-dim)

Migration 004 defines `search_similar_recipes` using `vector(384)` against the `recipe_embeddings` table. The rest of the system uses 1536-dim against `recipes.embedding_vector`. Unclear who calls this — `[verify]` whether any external integration (n8n, legacy server.js) uses it. If no, drop it in a follow-up cleanup.

## Notes

- **Why search bar gets full-text not semantic:** see RAG_AUDIT.md §1. Personal collection scale + user typing literal terms + latency budget = full-text is correct primitive. Semantic search is the right tool for the chat agent (natural-language input modality) and similar-rail (no good lexical analog).
- **Recommendations RPC is SQL scoring, not embeddings:** `get_recipe_recommendations` returns recipes scored by structured signals (difficulty, tags, rating, prep_time, reactions). Embeddings only become relevant as an optional re-rank (Phase 4b).
- **Migration locality:** All new SQL stays in `supabase/migrations/` locally. User deploys per HARD RULE.
- **No new edge functions in this MOP.** Phase 4's planner suggestions call `get_recipe_recommendations` directly from `api.ts`. The original draft proposed a `meal-suggestions/` edge function with an LLM call — dropped because pure SQL scoring is faster, cheaper, and good enough for v1.
