## Scope of Work

### Phase 1: `migration-rls-checker` subagent
**Files affected:** `.claude/agents/migration-rls-checker.md` (new)

Greps every new SQL file under `supabase/migrations/` for:
- `CREATE TABLE` without matching `ENABLE ROW LEVEL SECURITY`
- Tables with no `CREATE POLICY` rows
- `SECURITY DEFINER` functions without `SET search_path = public`

Read-only; reports violations with file + line. Reuses qa-auditor's report format.

### Phase 2: PreToolUse hook — block remote-DB migration commands
**Files affected:** `.claude/settings.json`

Enforces the HARD RULE (never push migrations to remote DB). Blocks any Bash invocation containing `supabase db push`, `supabase migration push`, or `--linked`.

Pure safety net. No quality-gate hooks (per MOP-0005 Notes).

### Phase 3: `/scaffold-api-method` skill
**Files affected:** `.claude/skills/scaffold-api-method.md` (new)

Single-shot procedure: given a method name + RPC/endpoint shape, generates the `api.ts` method, the MSW handler in `src/test/msw/handlers.ts`, and the matching test block in `src/services/__tests__/api.test.ts`.

Accelerates MOP-0005 Phase 1 in-flight work.

### Phase 4: `recipe-pipeline-tester` subagent + fixture set
**Files affected:** `.claude/agents/recipe-pipeline-tester.md` (new), `supabase/functions/recipe-pipeline/__fixtures__/` (new)

Subagent runs URL/text/video adapters against a fixture set and diffs against golden JSON. Catches extraction regressions that today only surface in production.

### Phase 5: `runbook-recorder` subagent
**Files affected:** `.claude/agents/runbook-recorder.md` (new)

After resolving a non-trivial bug, drafts a `docs/RUNBOOK.md` entry from the diff + commit message. Proposes; does not commit.

### Phase 6: `security-auditor` subagent
**Files affected:** `.claude/agents/security-auditor.md` (new)

Adapted from an external reference pattern, tailored to MealPrep:

- **Secret exposure scan** — API keys / tokens in client-side code, service role keys outside server context, `.env` leakage via git, logged auth headers / emails / full request bodies in edge functions
- **RLS enforcement check** — every table has RLS enabled + at least one policy; no client-side filtering as RLS substitute
- **Edge function security** — CORS handling, JWT validation, input sanitization, no exposed internal error details, service role key usage audit
- **HARD RULE adherence** — no `supabase db push` / `--linked` in any committed file
- **OWASP LLM Top 10 alignment** — prompt injection surface (especially `url-adapter.ts` per MOP-0008 risks), output validation on extraction, tool-output handling
- **`auth.uid()` discipline** — no RPC accepts `user_id` as a parameter; all `SECURITY DEFINER` functions have `SET search_path = public`

Read-only; reports violations. Sibling to `qa-auditor` (architectural) — this is security-specific. Audit-first-report-second protocol + run log per project standard.

### Phase 7: `architecture-guard.md` prompt doc
**Files affected:** `docs/prompts/architecture-guard.md` (new)

Pre/post change compliance checklist that any session can read before/after non-trivial changes. Adapted from an external reference pattern.

Contains:
- **Pre-change checks** — read CLAUDE.md, identify scope, check for HARD RULE conflicts, identify whether an ADR is warranted (per `ADR_AUTHORING_GUIDE.md` criteria)
- **Post-change checks** — RLS still enabled on touched tables, `auth.uid()` still used (no `user_id` parameter creep), prompts still in `_shared/recipe-prompts.ts` (no new inline prompts), `api.ts` still the only HTTP boundary, tests still pass
- **Change classification** — A (refactor, no architectural impact) / B (extension, follows existing patterns) / C (deviation, requires ADR).

Referenced by `doc-adherence`, `qa-auditor`, and `security-auditor`. The MOP-0010 `/post-change-check` skill executes these checks programmatically against changed files.
