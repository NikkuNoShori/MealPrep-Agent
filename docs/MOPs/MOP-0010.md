## Summary

MOPs today have markdown checkbox acceptance criteria — read by humans, checked by trust. Result: MOP-0004 and MOP-0005 sit at `draft` despite substantial shipped work. This MOP introduces a **lockticket** system where MOPs declare their acceptance criteria as machine-checkable assertions (file existence, command exit codes, grep patterns, test names) and a verifier skill enforces transitions. A MOP cannot become `completed` until every assertion passes.

---

## Scope of Work

### Phase 1: Status lifecycle + MOP schema
**Files affected:** `docs/MOPs/MOP_TEMPLATE.md`, `docs/MOPs/REGISTRY.md`

- Add `in_progress`, `verifying`, `blocked` statuses to the lifecycle.
- Add `## Verification` section to the template (YAML block of assertions).
- Add `## Scope Map` (file globs identifying the MOP's territory).
- Document assertion types: `file-exists`, `grep`, `command`, `test-passes`, `human`.

### Phase 2: `/verify-mop` skill
**Files affected:** `.claude/skills/verify-mop.md` (new)

Single-shot procedure:
1. Parse the named MOP's `## Verification` block
2. Execute each assertion in order, report ✅/❌ per item
3. If all pass → propose a `git diff` to flip status in registry + MOP header + `Date Completed`
4. If any fail → emit a blocked report; refuse to flip status
5. Never auto-commits — user holds the pen

### Phase 3: `/post-change-check` skill
**Files affected:** `.claude/skills/post-change-check.md` (new)

After a commit touches files matching any active MOP's `Scope Map`:
1. Re-run that MOP's verification block
2. Run `doc-keeper` against the touched scope
3. Run `qa-auditor` against the branch diff
4. Run relevant `data-integrity` suites
5. Report pass/fail; nothing auto-commits, nothing auto-merges

### Phase 4: Retrofit existing MOPs
**Files affected:** `docs/MOPs/MOP-0003.md` through `docs/MOPs/MOP-0009.md`

Add `## Verification` blocks to existing MOPs. MOP-0005 retrofitted first as the proof case (its acceptance criteria are already concrete). MOP-0008 already ships with the new format.
