## Summary

`meal_plans` today stores `meals` and `grocery_list` as JSONB on a single row (per migration 001:136). This MOP normalizes them into row-shaped child tables (`meal_plan_entries`, `grocery_list_items`) with proper foreign keys, per-row RLS, and indexable date/slot columns.

**This MOP is deferred.** The current JSONB shape is workable and the architectural cost of premature normalization is real. Execution is triggered by one of the conditions below — not on schedule.

Source: identified during MOP-0008 design (architect surprise: tool catalogs assumed normalized shape).

---

## Trigger Conditions

Execute this MOP when **any one** of the following becomes a measured problem:

| Trigger | Detection | Why it fires |
|---|---|---|
| **MOP-0007 query friction** | "Suggest a week" or "Recommended for you" implementation requires JSONB unnest gymnastics or per-row scans across all meal plans | Recipe-history scoring needs row-shape |
| **Concurrent household editing** | Two household members report lost meal-plan edits within 5 min of each other (last-write-wins on JSONB) | Document-level locking can't grant per-slot isolation |
| **Dangling recipe references** | A `recipe_id` in JSONB points at a deleted recipe and causes a render error or RAG miss | FK constraints would catch at delete time |
| **Analytics need** | A feature requires cross-plan aggregation (e.g., "what % of slots are dinner", "household chicken frequency", "grocery items by category over time") | GROUP BY on row data is trivial; on JSONB it's expensive |
| **MOP-0008 tool friction** | Bot tools `assign_recipe_to_meal_plan_slot` or `add_to_grocery_list` hit JSONB consistency bugs (race conditions on read-modify-write) | Row-shape eliminates the RMW window |

If none of these are measured, this MOP stays deferred — do not execute on a hunch.

## Scope of Work

### Phase 1: Schema design + migration authoring
**Files affected:** `supabase/migrations/YYYYMMDD_meal_plan_normalization.sql` (new), `supabase/migrations/YYYYMMDD_meal_plan_backfill.sql` (new)

Author migration files locally (HARD RULE: do not push — user handles deploys).

```sql
CREATE TABLE meal_plan_entries (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  meal_plan_id uuid NOT NULL REFERENCES meal_plans(id) ON DELETE CASCADE,
  date date NOT NULL,
  slot text NOT NULL CHECK (slot IN ('breakfast','lunch','dinner','snack')),
  recipe_id uuid REFERENCES recipes(id) ON DELETE SET NULL,
  servings integer,
  notes text,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now(),
  UNIQUE (meal_plan_id, date, slot)
);
CREATE INDEX idx_mpe_meal_plan_id ON meal_plan_entries(meal_plan_id);
CREATE INDEX idx_mpe_recipe_id ON meal_plan_entries(recipe_id);
CREATE INDEX idx_mpe_date ON meal_plan_entries(date);
ALTER TABLE meal_plan_entries ENABLE ROW LEVEL SECURITY;
-- policies: same visibility as parent meal_plans

CREATE TABLE grocery_list_items (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  meal_plan_id uuid NOT NULL REFERENCES meal_plans(id) ON DELETE CASCADE,
  item text NOT NULL,
  amount numeric,
  unit text,
  category text,
  source text CHECK (source IN ('auto-from-recipe','chat','manual')),
  source_recipe_id uuid REFERENCES recipes(id) ON DELETE SET NULL,
  is_checked boolean NOT NULL DEFAULT false,
  position integer,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);
CREATE INDEX idx_gli_meal_plan_id ON grocery_list_items(meal_plan_id);
CREATE INDEX idx_gli_source_recipe_id ON grocery_list_items(source_recipe_id);
ALTER TABLE grocery_list_items ENABLE ROW LEVEL SECURITY;
-- policies: same visibility as parent meal_plans
```

Backfill migration: insert from existing JSONB into new tables. Keep JSONB columns intact during transition.

### Phase 2: Dual-write in `api.ts`
**Files affected:** `src/services/api.ts` (meal-plan methods, lines 379–526), tests in `src/services/__tests__/api.test.ts`

Modify `createMealPlan`, `updateMealPlan`, `addToGroceryList`, `assignMealPlanSlot` etc. to write to BOTH JSONB columns AND new child tables. Reads continue from JSONB.

Dual-write enables incremental cutover without downtime and gives a safety window to detect divergence.

### Phase 3: Switch reads to child tables + UI updates
**Files affected:** `src/services/api.ts`, `src/pages/MealPlanner.tsx`, `src/components/grocery/*`, `src/utils/ingredientAggregator.ts`

- `api.ts` meal-plan reads now JOIN from `meal_plans` + `meal_plan_entries` + `grocery_list_items`, returning the same shape the frontend already expects.
- UI components unchanged at this point (shape preserved).
- `ingredientAggregator.ts` may be simplifiable — some aggregation moves to SQL.

### Phase 4: Update chat-api tool handlers
**Files affected:** `supabase/functions/chat-api/tools/handlers.ts` (from MOP-0008)

- `assign_recipe_to_meal_plan_slot` — write to `meal_plan_entries`, use `UNIQUE (meal_plan_id, date, slot)` for race-safe upsert.
- `add_to_grocery_list` — INSERT into `grocery_list_items`.
- Slot-occupied check (for conditional-confirmation flow) becomes a simple SELECT.

### Phase 5: Drop JSONB columns
**Files affected:** `supabase/migrations/YYYYMMDD_drop_meal_plans_jsonb.sql` (new), `src/services/api.ts`, regenerated types (depends on MOP-0006)

After production verification of read parity (Phase 3 ran clean for ≥ 1 week of usage):

```sql
ALTER TABLE meal_plans DROP COLUMN meals;
ALTER TABLE meal_plans DROP COLUMN grocery_list;
```

Remove dual-write code from `api.ts`. Regenerate types.

## Risks

1. **Data migration on production.** User handles deploys (HARD RULE). The migration must be transactional and idempotent. Dual-write phase de-risks by allowing verification before drop.
2. **RLS policy bugs.** New tables, new policies. Test with multiple household members before trusting.
3. **Race conditions on UNIQUE constraint.** Slot assignment must use `INSERT ... ON CONFLICT (meal_plan_id, date, slot) DO UPDATE` to be race-safe.
4. **Frontend breakage during transition.** Reads must return the same shape until UI is updated. Don't change UI consumers in the same phase as the read switch.
5. **MOP-0006 dependency.** Type regeneration requires generated Supabase types. If MOP-0006 isn't shipped first, types are hand-maintained — extra friction.
6. **MOP-0008 coupling.** If MOP-0008 is already in production when this fires, tool handlers must be updated in Phase 4. If MOP-0008 hasn't shipped yet, this MOP changes MOP-0008's tool handler design.

## Notes

- **Why not just keep JSONB.** JSONB models documents well, but `meal_plans` is increasingly being treated as a relational concept (per-slot edits, per-item check-off, history aggregation). Document semantics fit "save a plan" but not "modify, query, aggregate." The split between document and row models becomes the cost.
- **Why not normalize now (pre-trigger).** Premature normalization spends real engineering time (migration + dual-write + UI verification + chat-api tool updates) on a benefit that isn't measured yet. The deferred-with-triggers shape captures the constraint without paying the cost.
- **Why not partial normalization.** Hybrid (e.g., normalize `grocery_list` but keep `meals` JSONB) is the worst of both worlds — two mental models for closely-related data. Commit to one model when you commit.
- **Status review cadence.** Re-evaluate trigger conditions at every MOP-0007 implementation milestone and every household-feature work session. Don't let this MOP rot in `draft` indefinitely — if 12 months pass without a trigger firing, that itself is evidence the JSONB shape is fine and this MOP can be `cancelled`.
