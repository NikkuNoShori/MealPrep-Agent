## Summary

The data layer (`src/services/api.ts` and friends) currently uses `any` extensively for snake/camel mapping, Supabase query results, and RPC response shapes. This MOP introduces generated TypeScript types from the Supabase schema, threads them through the API client, and removes the `@typescript-eslint/no-explicit-any` rule suspension currently documented in `.eslintrc.cjs`.

---

## Current State

- **`@typescript-eslint/no-explicit-any` is `off`** in `.eslintrc.cjs` because the codebase has 200+ `any` usages, concentrated in the data layer.
- **`snakeToCamel` / `camelToSnake`** in [src/utils/case.ts](../../src/utils/case.ts) are typed `any → any`. Round-trip behavior is documented but not type-safe.
- **Supabase queries** in [src/services/api.ts](../../src/services/api.ts) use `(supabase.from('table') as any)` casts in several places to silence type errors against an untyped client.
- **RPC responses** (`rpc('get_my_household')`, `rpc('toggle_recipe_reaction')`, etc.) are not typed — callers cast to `any` or use ad-hoc interfaces.
- **No generated types file** — Supabase CLI's `gen types typescript` has not been run; there's no `src/types/database.ts`.

## Scope of Work

### Phase 0: Generate & wire types
**Files affected:** `package.json`, `src/types/database.ts` (new), `src/services/supabase.ts`

1. Add an npm script: `"types:supabase": "supabase gen types typescript --local > src/types/database.ts"`.
2. Run against local Supabase to produce `src/types/database.ts`.
3. Update `src/services/supabase.ts` to type the client: `createClient<Database>(...)`.
4. Add the script to a regenerate-on-migration workflow (manual for now; CI hook is a follow-up).

### Phase 1: Type the API client surface
**Files affected:** `src/services/api.ts`

1. Replace `(supabase.from('table') as any)` casts with the now-typed client.
2. Type RPC calls explicitly: `rpc<HouseholdResponse>('get_my_household')`.
3. Type return values of API methods (recipes, household, invites, collections, meal plans, preferences, reactions).
4. Where `any` remains, replace with `unknown` + narrowing, or with a documented interface.

### Phase 2: Type the case-conversion utilities
**Files affected:** `src/utils/case.ts`, `src/utils/__tests__/case.test.ts`

1. Add generic type parameters to `snakeToCamel<T>` and `camelToSnake<T>` so callers carry shape information through the conversion.
2. Add type-level tests (compile-time assertions) for known recipe shapes.
3. Document the `userId` drop in the type signature (not just a comment) — e.g., `Omit<T, 'userId'>` on the snake side.

### Phase 3: Re-enable the lint rule
**Files affected:** `.eslintrc.cjs`

1. Remove the `@typescript-eslint/no-explicit-any: 'off'` line and the comment pointing here.
2. Run `npm run lint` and address remaining violations (expected: a handful of intentional `any` in third-party-shape boundaries — escalate to `unknown` or per-line disable with justification).

## Notes

- **Why now (background):** The MOP-0005 lint cleanup paused this rule because the data layer's `any` usage is structural debt, not import hygiene. Splitting it out keeps "get tests + lint running" surgical and gives type-hardening its own scope.
- **Risk:** Tighter types will surface latent shape mismatches (e.g., a frontend assumes `recipe.imageUrl` exists, but the Supabase schema marks it nullable). Each surfacing is a real bug and should be fixed in-place rather than papered over with `!` non-null assertions.
- **Local-Supabase requirement:** `supabase gen types typescript --local` reads from a running local Supabase instance. Per the project's hard rule, never run `--linked` or modify the remote schema during type generation.
- **Edge functions out of scope:** This MOP types the frontend client only. Edge function type-tightening (`supabase/functions/`) belongs in a follow-on if needed — those run on Deno and have their own type surface.
