## Summary

Split from MOP-0005 Phase 4. End-to-end browser testing belongs in its own MOP because it requires a separate runner (Playwright), separate config, separate CI considerations, and a separate authoring style from unit/integration tests. Splitting it lets MOP-0005 promote to `complete` once Phases 0-3 + 5 finish, without E2E gating.

This MOP scopes the initial Playwright setup and a thin golden-path E2E suite. Long-term E2E growth is captured in the acceptance criteria, not in this MOP.

## Scope of Work

### Phase 1: Install + configure
**Files affected:** `package.json`, `playwright.config.ts` (new), `.gitignore`

1. `npm i -D @playwright/test`
2. `npx playwright install` (chromium only initially; firefox/webkit later)
3. Create `playwright.config.ts` with:
   - `testDir: 'e2e'`
   - `baseURL: 'http://localhost:5173'`
   - `webServer` config that runs `npm run dev` before tests
   - `use: { trace: 'on-first-retry', screenshot: 'only-on-failure' }`
   - `projects: [{ name: 'chromium', use: devices['Desktop Chrome'] }]`
4. Add scripts:
   - `"test:e2e": "playwright test"`
   - `"test:e2e:ui": "playwright test --ui"`
5. Add `test-results/`, `playwright-report/`, `e2e/.auth/` to `.gitignore`

### Phase 2: Test infrastructure
**Files affected:** `e2e/fixtures/auth.ts` (new), `e2e/fixtures/test-data.ts` (new)

- Auth fixture: programmatically signs in as a test user before each test (uses Supabase Auth API + storage state)
- Test data fixture: seeds a known recipe + meal plan + household state via local Supabase, cleans up after
- Both fixtures use local Supabase only (HARD RULE — never against remote)

### Phase 3: Golden-path E2E (P0)
**Files affected:** `e2e/golden-path.spec.ts` (new)

Five scenarios from MOP-0005 §Phase 4 table:
1. Signup → household created → user lands on Dashboard
2. Invite owner → invitee signup → accept → invitee sees household recipes
3. Recipe lifecycle: create → set visibility (public/household/private) → verify in correct feed
4. Role management: owner promotes member → admin UI appears → owner demotes → admin UI hidden
5. Collection management: create → add recipes → rename → delete

### Phase 4: Chat E2E (P1, gated on MOP-0008)
**Files affected:** `e2e/chat.spec.ts` (new)

Once MOP-0008 ships the tool-using agent:
- Single-intent: "find chicken recipes" returns results
- Multi-intent: "find pasta and add it to Tuesday dinner" produces both effects
- Destructive: "delete the carbonara" prompts for confirmation; no delete on cancel
- Confirmation persistence within session

### Phase 5: CI integration (deferred)
**Files affected:** `.github/workflows/e2e.yml` (new — when CI exists)

Currently MealPrep has no CI. When CI is set up, add a Playwright run step that:
- Spins up local Supabase via `supabase start`
- Runs `npm run test:e2e` against the dev server
- Uploads `playwright-report/` on failure
- Gates merges on green

## Notes

- **Local Supabase only.** Every E2E test runs against a local Supabase instance. Tests that touch the remote DB are not acceptable (HARD RULE).
- **No production data.** Auth fixture creates throwaway test users with predictable IDs (e.g., `e2e-user-<uuid>`); test data fixture cleans up after each spec.
- **Why chromium only initially.** Cross-browser coverage is valuable but the marginal catch rate is low for a project at MealPrep's scale. Adding firefox/webkit is a 1-line config change when needed.
- **Parallel with MOP-0012.** Test fixtures (MOP-0012) and E2E setup (this MOP) are independent — can be built in parallel.
- **Sequence vs MOP-0008.** MOP-0013 Phase 1-3 do not depend on MOP-0008. Phase 4 (chat E2E) does — defer Phase 4 until MOP-0008's chat-api migration is shipped.
- **CI is a non-blocker.** MealPrep has no CI today. The E2E suite is valuable even when run locally before commits. Add CI later (Phase 5) without it gating earlier phases.
