## Summary

Replace `chat-api`'s single-shot intent detection (one LLM call classifies → routes to one of three handlers) with a tool-using agent: one LLM call receives the user message + a tool catalog and decides which tools to invoke (zero, one, many, or chained). This unblocks multi-step queries like "find my chicken recipes safe for the kids and add two to next week's plan" that the current router cannot handle.

This is **Phase 1** of the AI agent migration from `docs/AI_INTEGRATION_AUDIT.md`. Phase 2 (supervisor + specialists) is intentionally deferred until evals show single-agent insufficient.

---

## Architectural Background

- **Current pattern:** Routing (Anthropic's pattern taxonomy). Limit: one intent per turn.
- **Target pattern:** Agent / autonomous tool use (Anthropic). Single LLM in a loop with a tool catalog.
- **Pattern choice rationale:** See `.claude/agents/cooking-bot-knowledge/architecture-patterns.md` §6. Supervisor + specialists is overkill until measurement justifies it.
- **Designed by:** `cooking-bot-architect` subagent (2026-06-01). Full design at [MOP-0008-design.md](MOP-0008-design.md).
- **Tool catalog:** 11 tools (read: 6, capture: 1, plan/cart: 2, destructive: 2). Under the "30+ tool" anti-pattern threshold.
- **Model:** `qwen/qwen-2.5-7b-instruct`, t=0.2, tool_choice=auto. Max 5 iterations per turn.

## Scope of Work

> Concrete steps from [MOP-0008-design.md](MOP-0008-design.md), ordered by dependency.

### Step 1: `chatWithTools` on the OpenRouter client
**Files affected:** `supabase/functions/_shared/openrouter-client.ts`

Add `chatWithTools(systemPrompt, messages, tools, model, options) → { content, tool_calls[] }`. POST to OpenRouter `/chat/completions` with OpenAI-compatible `tools` + `tool_choice` (Qwen 2.5 supports the format via OpenRouter passthrough). Export `ChatMessage` and `ToolSpec` types.

### Step 2: Move `RAG_RESPONSE_PROMPT` into the registry
**Files affected:** `supabase/functions/_shared/recipe-prompts.ts`, `supabase/functions/chat-api/index.ts`

Extract the inline prompt from `chat-api/index.ts:184–193` into the shared registry.

### Step 3: Add agent prompts to the registry
**Files affected:** `supabase/functions/_shared/recipe-prompts.ts`

Append `CHAT_AGENT_SYSTEM_PROMPT` (Chef Marcus + 6 hard rules) and `SUBSTITUTION_PROMPT` (used by the substitution tool). Mark `INTENT_DETECTION_PROMPT` `@deprecated`.

### Step 4: Tool catalog + dispatcher
**Files affected:** `supabase/functions/chat-api/tools/catalog.ts` (new), `supabase/functions/chat-api/tools/dispatch.ts` (new)

`catalog.ts` exports `TOOL_CATALOG`, `DESTRUCTIVE_TOOLS`, `CONDITIONALLY_DESTRUCTIVE`. `dispatch.ts` exports `dispatchTool(name, args, ctx)` that schema-validates args via Ajv (or a 60-line subset checker), looks up the handler, validates output, and returns a typed `ToolResult`.

### Step 5: Tool handlers (11 tools)
**Files affected:** `supabase/functions/chat-api/tools/handlers.ts` (new)

One exported function per tool. All use the user-scoped `ctx.supabase` so RLS enforces visibility. No handler accepts `user_id` from args — it comes from JWT. Extraction handler invokes existing `recipe-pipeline/extract-only` (no re-implementation).

### Step 6: Agent loop
**Files affected:** `supabase/functions/chat-api/agent-loop.ts` (new)

`runAgentLoop(input, ctx) → AgentReply` with `MAX_ITERS = 5`. Wraps tool outputs in `<tool_result>` markers (defense-in-depth against tool-output prompt injection). Destructive tools short-circuit with `pendingConfirmation` envelope.

### Step 7: Wire into `handleSendMessage`
**Files affected:** `supabase/functions/chat-api/index.ts`

Replace lines 485–532 (router) with `runAgentLoop` call. Add `confirmAction` short-circuit path. Remove `detectIntent`, `handleRAGSearch`, `extractRecipe`, `handleGeneralChat`. Keep `handleGetHistory`, `handleClearHistory`, image upload.

### Step 8: Frontend contract
**Files affected:** `src/services/api.ts`, `src/components/chat/*`

Add `pendingConfirmation` to response types and `confirmAction` to request `context`. Chat UI renders confirmation as an inline message with Confirm/Cancel.

### Step 9: Tests
**Files affected:** `supabase/functions/chat-api/__tests__/agent-loop.test.ts` (new, Deno test), `src/services/__tests__/chatAgent.test.ts` (new, Vitest+MSW), `supabase/functions/chat-api/__tests__/fixtures/golden.json` (new)

30-prompt golden set (10 single-intent, 10 multi-intent, 10 destructive-confirm). See `Verification` block.

### Step 10: Docs
**Files affected:** `docs/ARCHITECTURE.md`, `docs/API.md`

Update chat-api flow diagram; document `pendingConfirmation` and `confirmAction` on the API.

## Notes

- **Why single agent, not supervisor.** Per `cooking-bot-knowledge/architecture-patterns.md`, multi-agent escalation requires measurement showing single-agent fails specific evals. We don't have that data yet. Phase 2 follows Phase 1 only if eval data justifies it.
- **Model choice.** Stay with Qwen 2.5 family (current chat-api default). Tool use is supported on Qwen 2.5 7B+ instruct variants. Final model + temperature settings pending architect output.
- **Latency budget.** Current chat-api responds in ~2-5s for general chat, ~3-8s for RAG. Tool-use loops can add multiple LLM hops — target: 95th percentile under 12s per user turn. If exceeded, revisit single-call vs multi-hop.
- **Cost budget.** Per-message cost will rise ~2-3x due to tool catalog tokens + tool result composition. Acceptable within Phase 1 if usage stays bounded (see `safety-and-guardrails.md` rate limits).
- **Dependency on MOP-0007.** Several tools wrap RAG RPCs. MOP-0007 (wiring those RPCs into the UI) does not block MOP-0008 — both can proceed in parallel; the tool implementations call the RPCs directly.
- **Dependency on MOP-0010.** The `verification` block uses the lockticket schema. Until MOP-0010 ships, items are checked by hand. Schema is forward-compatible.
