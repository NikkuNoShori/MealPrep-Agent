## Summary

Replace `chat-api`'s single-shot intent detection (one LLM call classifies → routes to one of three handlers) with a tool-using agent: one LLM call receives the user message + a tool catalog and decides which tools to invoke (zero, one, many, or chained). This unblocks multi-step queries like "find my chicken recipes safe for the kids and add two to next week's plan" that the current router cannot handle.

This is **Phase 1** of the AI agent migration from `docs/AI_INTEGRATION_AUDIT.md`. Phase 2 (supervisor + specialists) is intentionally deferred until evals show single-agent insufficient.

---

## Architectural Background

- **Current pattern:** Routing (Anthropic's pattern taxonomy). Limit: one intent per turn.
- **Target pattern:** Agent / autonomous tool use (Anthropic). Single LLM in a loop with a tool catalog.
- **Pattern choice rationale:** See `.claude/agents/cooking-bot-knowledge/architecture-patterns.md` §6. Supervisor + specialists is overkill until measurement justifies it.
- **Designed by:** `cooking-bot-architect` subagent (2026-06-01). Full design at [MOP-0008-design.md](MOP-0008-design.md).
- **Tool catalog:** 12 tools (read: 7, capture: 1, plan/cart: 2, destructive: 2). Under the "30+ tool" anti-pattern threshold. **Addendum 1** (this document, below) adds `web_search_recipe` to the design's original 11; the design doc remains the source for tools 1–11.
- **Model:** `qwen/qwen-2.5-7b-instruct`, t=0.2, tool_choice=auto. Max 5 iterations per turn.

## Notes

- **Why single agent, not supervisor.** Per `cooking-bot-knowledge/architecture-patterns.md`, multi-agent escalation requires measurement showing single-agent fails specific evals. We don't have that data yet. Phase 2 follows Phase 1 only if eval data justifies it.
- **Model choice.** Stay with Qwen 2.5 family (current chat-api default). Tool use is supported on Qwen 2.5 7B+ instruct variants. Final model + temperature settings pending architect output.
- **Latency budget.** Current chat-api responds in ~2-5s for general chat, ~3-8s for RAG. Tool-use loops can add multiple LLM hops — target: 95th percentile under 12s per user turn. If exceeded, revisit single-call vs multi-hop.
- **Cost budget.** Per-message cost will rise ~2-3x due to tool catalog tokens + tool result composition. Acceptable within Phase 1 if usage stays bounded (see `safety-and-guardrails.md` rate limits).
- **Dependency on MOP-0007.** Several tools wrap RAG RPCs. MOP-0007 (wiring those RPCs into the UI) does not block MOP-0008 — both can proceed in parallel; the tool implementations call the RPCs directly.
- **Dependency on MOP-0010.** The `verification` block uses the lockticket schema. Until MOP-0010 ships, items are checked by hand. Schema is forward-compatible.

## Addendum 1: `web_search_recipe` Tool (2026-06-01)

> **Why.** Triggered by user feedback: "I'm looking to go grab a devilled egg recipe from the web." The original 11-tool catalog requires the user to supply a URL (`extract_recipe_from_source`), leaving the very common "find a recipe online for me" path unaddressed. Adding a 12th read-only tool — `web_search_recipe` — lets the agent compose `web_search_recipe` → `extract_recipe_from_source` autonomously.
>
> This addendum **extends** [MOP-0008-design.md](MOP-0008-design.md); the design doc remains the source for tools 1–11. Bumps in this MOP's headers (Architectural Background, Step 5) reflect the new total.

### Catalog change

| | Before | After |
|---|---|---|
| Total tools | 11 | 12 |
| Read tools | 6 | 7 |
| Capture | 1 | 1 |
| Plan/cart | 2 | 2 |
| Destructive | 2 | 2 |

### Tool schema

```json
{
  "name": "web_search_recipe",
  "description": "Search the public web for recipes matching a query. Returns up to 5 candidate results (title, URL, source domain, snippet) ranked by relevance. Does NOT extract or save. Use when the user asks to find a recipe online, asks for inspiration outside their saved collection, or when `search_recipes` returns no matches. The agent typically chains a follow-up `extract_recipe_from_source` call with one of the returned URLs (either auto-selected when the top result is clearly relevant, or after presenting candidates to the user). Read-only.",
  "destructive": false,
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "minLength": 1,
        "description": "Natural-language recipe search, e.g. 'devilled eggs', 'gluten-free chocolate chip cookies', 'one-pot weeknight pasta'."
      },
      "max_results": {
        "type": "integer",
        "minimum": 1,
        "maximum": 5,
        "default": 3
      },
      "site_filter": {
        "type": "string",
        "description": "Optional domain to restrict the search to (e.g. 'seriouseats.com'). Use only when the user explicitly names a source."
      }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

### Tool result shape

Conforms to the catalog-wide `ToolResult` envelope from design.md Step 5.

```ts
type WebSearchRecipeResult =
  | {
      ok: true;
      data: {
        candidates: Array<{
          title: string;
          url: string;            // Suitable for direct pass-through to extract_recipe_from_source
          source_domain: string;  // Host portion, e.g. "seriouseats.com"
          snippet: string;        // ≤ 200-char excerpt for ranking display
        }>;
        provider: "tavily" | "brave" | "serper"; // Telemetry only
      };
    }
  | {
      ok: false;
      error:
        | "PROVIDER_UNAVAILABLE"
        | "RATE_LIMITED"
        | "NO_RESULTS"
        | "PROVIDER_NOT_CONFIGURED";
      retryable: boolean;
    };
```

### Provider abstraction

**New file:** `supabase/functions/_shared/web-search-client.ts`

- Default provider: **Tavily** (recipe-friendly relevance, ~$0.005/search, free tier ~1k queries/mo).
- Drop-in alternatives via the same interface: **Brave Search**, **Serper**.
- Provider selected via `WEB_SEARCH_PROVIDER` env var (default `tavily`).
- API key via `WEB_SEARCH_API_KEY` (read only inside the shared client; never referenced from handlers).
- **Capability gating:** if `WEB_SEARCH_API_KEY` is unset at function init, `web_search_recipe` is omitted from the agent's tool catalog at startup rather than failing at call time. Agent simply lacks the capability.

### Handler addition (Step 5)

Append to `supabase/functions/chat-api/tools/handlers.ts`:

- `web_search_recipe` — call shared `webSearch.query({ query, maxResults, siteFilter })`; map provider response to `WebSearchRecipeResult.data.candidates`. Map provider 5xx / timeouts to `{ ok: false, error: "PROVIDER_UNAVAILABLE", retryable: true }`. Empty results map to `{ ok: false, error: "NO_RESULTS", retryable: false }` so the agent can fall back to an explanation rather than retry.

No `ctx.supabase` access, no RLS surface, no DB writes.

### Agent prompt addition (Step 3)

Append to `CHAT_AGENT_SYSTEM_PROMPT`:

> When the user asks for a recipe and `search_recipes` returns no matches, OR the user explicitly asks to "find online" / "search the web" / "look up" / "grab" a recipe — call `web_search_recipe`, then `extract_recipe_from_source` with the most relevant URL. Surface the chosen source domain ("Found one from seriouseats.com — pulling it in now"). Never fabricate URLs; only use URLs returned by `web_search_recipe`. If the top candidate is not clearly the best match (multiple equally-relevant domains, ambiguous query, user asked for "options"), present the candidate list and ask which to extract.

### Cost and latency impact

- **Cost.** Tavily ~$0.005/search. Turns that hit `web_search_recipe` will roughly double the per-turn budget from `cost-per-turn` ($0.005 → ~$0.010). Acceptable for an opt-in path; do not promote `web_search_recipe` over `search_recipes` for queries that can be served locally.
- **Latency.** +400–1200 ms per search call. The expected `web_search_recipe` → `extract_recipe_from_source` chain will dominate the `latency-multi-tool` bucket: target ≤ 8 s p50 for these specifically (vs. the original ≤ 6 s for purely-local multi-tool turns).

### Safety notes

- **Untrusted snippet text.** Search results are third-party. Snippet content lives inside the existing `<tool_result>...</tool_result>` markers (design.md Step 6) for prompt-injection isolation. Tested via `web-search-injection-resisted`.
- **URL surface.** Returned URLs flow into `extract_recipe_from_source` → `recipe-pipeline` URL adapter, which is already a path that hits external URLs. No new sandbox surface.
- **Provider failures.** Must not block other tool calls in the same loop iteration. Handler returns `ok: false` with `retryable` set; the agent surfaces the failure conversationally.

### Open question (resolve before implementation)

- **Auto-extract vs. ask-first.** Should the agent chain `web_search_recipe` → `extract_recipe_from_source` autonomously, or always present the candidate list and require selection? Phase 1 default: **chain autonomously when one candidate is clearly best (named domain, exact-title match); otherwise present candidates.** Revisit after golden evals — the `golden-web-search` bucket should include both kinds of prompts.
