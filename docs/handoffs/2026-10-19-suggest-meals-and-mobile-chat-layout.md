- `4819a61` — `fix(mobile)`: **the actual root-cause fix.** `svh` on `Layout.tsx` alone didn't fix it either — user tested on a real Galaxy S26 Ultra (Chrome) and an iPhone 16 Pro Max (Safari) and the composer was still fully missing on both, while desktop Chrome's device-emulated S20 view looked fine the whole time (emulation doesn't replicate real address-bar/keyboard viewport resize behavior). Root cause: `html`, `body`, `#root` in `index.css` were sized with `height:100%`, a *separate* height source from `Layout.tsx`'s own viewport-unit div further down the tree — two independent height calculations that can disagree on real mobile engines. Fix moves the viewport unit to the actual root of the sealed height chain (`html`/`body`/`#root`), with `Layout.tsx` now just inheriting via `h-full`. Used `@supports (height: 100svh)` rather than stacked `height:` declarations, because this project's CSS minifier was caught collapsing repeated same-property declarations down to just the last one (confirmed in actual build output) — which would have silently deleted the `height:100%` fallback for non-`svh` browsers if left as plain stacked declarations. Also added `viewport-fit=cover` to `index.html`'s viewport meta tag, since the `env(safe-area-inset-bottom)` padding added to the chat composer in this same commit was otherwise always resolving to `0`.

## Decisions and reasoning

**Why four separate commits for what's arguably one mobile bug**: each fix was pushed and tested live by the user between rounds, and each round genuinely changed hypothesis (missing entirely → clipped-needs-tap → still broken on real hardware → root-cause found). Squashing these into one commit would lose the diagnostic trail of what was tried and ruled out, which matters here because the first three attempts *didn't work* — a future session re-touching this file should see that `dvh` and `svh`-on-Layout-alone were both tried and failed, not re-attempt them.

**Desktop Chrome device emulation is not a reliable test for this class of bug.** The user explicitly checked a Galaxy S20 profile in desktop DevTools mid-session and it looked fine — the bug never reproduced there. Emulation fakes a static viewport size; it doesn't replicate the real browser chrome resize/settle behavior (address bar show/hide, keyboard open) that was the actual trigger. Worth remembering for any future viewport-unit bug on this project — real-device testing is required, not just emulation.

**Why `@supports` instead of stacked `height:` declarations**: discovered mid-session that this project's CSS minifier (default Vite/esbuild or lightningcss, not separately configured) collapses multiple `height:` lines on the same selector down to just the last one in the *built* CSS — verified by grepping the actual `dist/assets/*.css` output. A naive `height:100%; height:100dvh; height:100svh;` fallback pattern (which relies on browsers skipping unsupported values and falling through to the last valid one) silently loses the fallback entirely once minified, because the minifier doesn't know `100svh` might be unsupported in some browser — it just sees three declarations of the same property and keeps the last. `@supports` branches are separate rules, so minification can't merge them away.
